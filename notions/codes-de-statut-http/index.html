Pourquoi ça existe

Une réponse doit dire si ça a marché.

Chaque fois que ton appli envoie une , elle reçoit une . Mais une réponse, ça peut être une bonne ou une mauvaise nouvelle. Avant même de lire les données, l'appli doit savoir : est-ce que ça a marché ? Et sinon, à qui la faute ?

Si chaque serveur l'écrivait avec ses propres mots, aucune appli ne pourrait comprendre tous les serveurs. Alors a fixé une règle commune : chaque réponse commence par un de trois chiffres. Le premier chiffre suffit pour savoir de quel côté chercher.

C'est aussi ce que tu regardes en premier quand une appli plante, ce que tu choisis quand tu écris une , et une question classique en entretien.

La grammaire

Lis d'abord le premier chiffre.

Le premier chiffre donne la famille, et la famille dit de quel côté chercher. Les deux autres chiffres précisent. Tu n'as pas besoin de tout retenir : connais les trois familles et une poignée de codes.

2xx

✅ Ça a marché

La demande était bonne, le serveur l'a traitée.

  • 200OK, voilà ce que tu as demandé
  • 201Créé (après un POST)
  • 204Fait, rien à renvoyer
4xx

🙋 La demande pose problème

Le serveur va bien. C'est ce qu'on lui demande qui ne va pas.

  • 400Demande mal formée
  • 401Pas connecté
  • 403Connecté, mais pas le droit
  • 404Introuvable
  • 409Conflit avec l'état actuel
5xx

🔥 Le serveur a un problème

La demande était peut-être bonne. Le serveur n'a pas réussi à faire son travail.

  • 500Erreur interne
  • 503Indisponible pour l'instant

Il existe aussi les 1xx (informations) et les 3xx (redirections : « c'est à une autre adresse »). Tu les croiseras moins.

À quoi ressemble une réponse

Le code arrive sur la toute première ligne, avant les données.

HTTP/1.1 404 Not Found
Content-Type: application/json

{ "erreur": "Post 999 introuvable" }

Le plus petit code qui le choisit

Côté serveur, en Java avec Spring : c'est toi qui décides du code.

Post post = posts.trouver(id);
if (post == null) {
    // la demande vise un post qui n'existe pas
    return ResponseEntity.status(404).build();
}
return ResponseEntity.ok(post);  // 200 + le post

Le monde réel

En équipe, le code dit où chercher.

Une vraie appli envoie des dizaines de requêtes par écran. Quand ça casse, le premier chiffre trie le problème en une seconde.

Problème 1

Trouver la requête qui casse.

L'écran s'affiche à moitié. Un développeur ouvre l' du navigateur : chaque requête y apparaît avec son code. Il cherche les 4xx et les 5xx, et chaque famille l'envoie à un endroit différent.

MéthodeURLStatut
Lance le chargement de l'écran.

Problème 2

Réessayer, ou pas.

Une appli bien faite toute seule quand c'est utile. Un 5xx est souvent passager : on réessaie en attendant un peu plus à chaque fois. Un 4xx ne changera pas : la même demande donnera la même réponse, réessayer ne sert à rien.

Avec l'IA

Elle propose, tu vérifies.

Ce qu'elle fait bien

Choisir le code d'un cas courant (créé, introuvable, pas connecté) et écrire le code Java qui le renvoie.

Ce que tu dois vérifier

Qu'elle ne renvoie pas 500 pour une demande invalide, ni 200 avec un message d'erreur caché dans les données. Pose-toi la question : qui est en faute, la demande ou le serveur ?

Question d'entretien

« Un client envoie un JSON mal formé et ton API répond 500. Qu'est-ce qui ne va pas ? »

Le problème vient de la demande, pas du serveur : il faut répondre 400 (demande mal formée). Un 500 fait croire à une panne : l'équipe reçoit une alerte pour rien, et le client peut réessayer en boucle une demande qui échouera toujours. En général, la cause est une exception qui n'est pas attrapée : on l'intercepte et on la transforme en 400 avec un message clair.

    Fiche · Les codes de statut HTTP

    L'essentiel sur un écran, à relire la veille.

    L'essentiel

    • Chaque réponse HTTP commence par un code de trois chiffres. Lis d'abord le premier.
    • 2xx ça a marché · 4xx la demande pose problème · 5xx le serveur a un problème.
    • Un serveur en bonne santé peut répondre une mauvaise nouvelle : 404, c'est le serveur qui dit calmement « ça n'existe pas ».
    • À connaître : 200 OK · 201 créé · 204 fait, rien à renvoyer · 400 mal formée · 401 pas connecté · 403 pas le droit · 404 introuvable · 409 conflit · 500 erreur interne · 503 indisponible.

    Les pièges

    • Croire que toute erreur est un problème de serveur : 4xx = la demande.
    • Renvoyer 500 pour une demande invalide : fausse alerte, réessais inutiles.
    • Renvoyer 200 avec {"erreur": …} dans les données : l'appli croit que tout va bien.
    • Réessayer un 4xx : la même demande donnera la même réponse.

    En vrai

    • Quand ça casse, on ouvre l'onglet Réseau : 4xx, on regarde la demande envoyée par l'appli ; 5xx, on lit les journaux du serveur.
    • La documentation Swagger d'une API liste, pour chaque route, les codes qu'elle peut renvoyer.
