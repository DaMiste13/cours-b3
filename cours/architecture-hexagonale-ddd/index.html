Un domaine au centre.
Le reste se branche.

Ce module apprend à ranger une application pour qu'elle reste facile à changer. Les règles du métier au milieu, la technique autour, branchée comme un appareil sur une prise. Puis à parler la langue du métier, et à dessiner le tout pour l'expliquer.

Les mots soulignés en pointillés s'expliquent : clique dessus.

Les flèches pointent vers le centre : le domaine ne connaît personne.

À quoi sert ce module

Parce qu'un code qui marche ne suffit pas.

Une application écrite « vite » marche le premier jour. Six mois plus tard, chaque changement en casse un autre, et plus personne n'ose y toucher. L' coûte un peu au début et rapporte longtemps. Ce module en donne trois bénéfices concrets.

Changer sans casser

On remplace la base de données ou le site web sans toucher aux règles du métier.

Tester sans tout lancer

Le cœur se teste seul, en une fraction de seconde, sans serveur ni base.

Parler la langue du métier

Les mêmes mots dans la bouche du client, de l'équipe et dans le code.

    Fiche · Architecture hexagonale et DDD

    Le module sur un écran, à relire la veille.

    À quoi il sert

    • Ranger le code pour qu'il reste facile à changer : le métier au centre, la technique branchée autour.
    • Tester le cœur seul, sans serveur ni base.
    • Modéliser le métier avec ses propres mots (DDD), puis documenter l'architecture (UML, décisions).

    Les trois pièges

    • Croire que l'hexagone, ce sont des dossiers. Ce qui compte, c'est le sens des dépendances : vers le centre.
    • Confondre port et adaptateur. Le port est la prise, déclarée par le domaine ; l'adaptateur est le câble, écrit avec la technique.
    • Laisser les règles du métier dans les services ou les contrôleurs. Elles vivent dans les entités et les agrégats.
